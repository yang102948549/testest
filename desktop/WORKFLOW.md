# 시험감독 배정 프로그램 워크플로우

기준일: 2026-10-01 · 제작자: 양양. 업무 흐름은 현재 구현이며 구매 인증·업데이트는 개발 예정인 목표 흐름이다.

## 1. 전체 업무 순서

새 고사 → 시험 일정·고사실 → 교사 명단·조건 확인 → 감독 방식·점수 설정 → 자동 배정 → 결과 검토 → 수동 조정·반영 → 저장·Excel 출력·JSON 백업.

### A. 시험 설정

1. 새 고사를 만들거나 기록에서 기존 고사를 연다.
2. (선택) ‘학교 설정’에서 컴시간 학교를 정하면 학년별 학급을 고사실로 불러오고, 교사 설정의 시간표 불러오기가 이 학교를 바로 사용한다. 설정하지 않아도 직접 입력·다른 학교 검색·엑셀 시간표로 모두 가능하다.
3. 학년별 교실, 복도 구역과 특별실을 등록한다.
4. 날짜·교시를 만들고 교시×학년 칸에서 과목과 적용 고사실을 선택한다.
5. 선택창에서 적용해야 변경이 반영된다. 시험이 없는 교시에 불필요한 자리가 생기지 않는지 확인한다.

### B. 명단과 배정 조건

1. 직접 입력, 표 붙여넣기, Excel/CSV/TSV, Google Sheets 링크 또는 컴시간 공개 데이터로 명단을 준비한다. 온라인 가져오기는 네트워크가 필요하다.
2. 미리보기에서 시트·제목 행·열 연결과 행별 오류를 확인하고 추가한다.
3. 교사별 담당 과목, 담임, 감독불가학급과 역할을 확인한다. 원본에 없는 조건이 자동 완성되었다고 간주하지 않는다.
4. 일반교사의 불가능 교시, 지정교사의 지정 교시와 자리 선호를 설정한다. 제외교사와 지정교사의 미체크 교시는 배정 대상이 아니다.
5. 미연결 학급·알 수 없는 역할을 정리한다. 조건이 누락되면 엔진이 실제 업무 조건을 알 수 없으므로 배정 전 검토가 필요하다.

### C. 감독 방식·점수

1. 일반 또는 정/부 감독을 선택한다.
2. 일반 모드는 교실·복도 가중치를 입력한다. 2·1은 기본값이며 변경 가능하다.
3. 정/부 모드는 건당 1점이며 단독 감독실을 교시별로 지정한다.
4. 전체·일일 횟수 기준은 참고 경고이다. 감독불가 조건을 대신하지 않는다.

### D. 자동 배정

1. 미반영 수동 변경은 먼저 반영하거나 취소한다.
2. 자리와 후보를 생성하고 필수 금지 제약을 적용한다.
3. 지정배치 → 충원 → 지정교사 자리 선호 → 일반교사 점수 범위 → 평균 절대 편차 순으로 최적화한다.
4. 취소하면 이전 결과를 유지한다. 완료하면 독립 검증 결과와 배치안을 보여준다.
5. ‘최적해 확인’과 ‘최적성 미확인’을 구분한다. 최적해 표시는 미배정 없음이나 입력의 완전성을 의미하지 않는다.

### E. 결과 검토·수동 조정

1. 교사별·고사실별 표, 점수, 빈자리, 지정 미충족과 참고 경고를 확인한다.
2. 빈자리는 후보 부재인지 동시간 경쟁인지 살핀다. 금지 조건을 무시해 자동 충원하지 않는다.
3. 같은 교시의 두 교사 칸을 선택해 교환하거나 빈 교사에게 옮긴다. 고사실별 화면에서는 후보를 선택하거나 해제한다.
4. 불가능한 교환·배정은 사유와 함께 거부한다. 가능한 수정은 임시 상태로 유지한다.
5. ‘변경사항 반영’으로 검증 후 저장하거나 되돌리기·취소한다. 수동 결과에 기존 최적성 증명을 표시하지 않는다.
6. 일정·교사 조건을 변경하면 재검증한다. 재검증은 잘못된 연결을 정리하는 작업이며 새 자동 배정과 다르다.

### F. 저장·출력

1. 저장 상태를 확인한다. 일반 입력은 자동 저장되고 Ctrl+S로 즉시 저장할 수 있다.
2. Excel로 배정표를 출력하고 고사 전체 이동·백업에는 JSON을 사용한다.
3. 기록에서 다시 열거나 JSON을 새 고사로 가져온다.
4. 종료 전 미반영 수정·저장 실패를 해결한다. 로컬 자동 저장과 직전본 백업이 외부 백업을 대신하지는 않는다.

## 2. 구매·첫 실행: 개발 예정

구매 → 공통 설치 EXE와 구매자별 `.license` 파일 수령 → 인증 입력 없는 설치 → 첫 실행 → ‘구매 인증 파일 선택’ → 서명 검증 → 사용자 데이터 폴더에 인증 저장 → 업무 화면.

- 취소·잘못된 파일·다른 제품용 파일은 미인증 상태로 남기고 재선택을 안내한다.
- 잘못된 파일로 기존 정상 인증을 덮어쓰지 않는다.
- 최초 인증 후 오프라인으로 사용하며 패치 때 인증 파일 재선택을 요구하지 않는 것을 목표로 한다.
- 현재의 설치 CD키 화면과 실행 시 키 붙여넣기 화면은 교체해야 한다. 아직 구현된 흐름이 아니다.

## 3. 사용자 업데이트: 개발 예정

실행 시 비동기 확인 또는 ‘업데이트 확인’ → 버전·변경사항 안내 → 다운로드 승인 → 다운로드·서명 검증 → ‘저장 후 업데이트’ → 임시 조정 처리·저장 성공·백업 확인 → 종료·설치 → 새 버전 실행·인증과 데이터 확인.

| 상황 | 기대 동작 |
|---|---|
| 인터넷 없음·서버 오류 | 업무 계속 사용, 나중에 재확인 |
| 사용자가 나중에 선택 | 강제 종료·설치 없음 |
| 다운로드 실패·손상·서명 불일치 | 새 파일 설치 중단, 현재 버전 유지 |
| 계산 중·미반영 변경·저장 실패 | 설치 보류, 해결 방법 안내 |
| 설치 과정 실패 | 데이터·인증 보존, 오류 기록·복구 안내. 자동 복구를 검증 없이 보장하지 않음 |
| 데이터 형식 변경 | 백업 후 검증된 마이그레이션, 실패 시 원본 보존 |

현재 1.2.0 EXE에는 업데이트 클라이언트가 없어 원격으로 이 기능을 받을 수 없다. 이미 사용 중인 사람이 있다면 새 방식의 첫 버전으로 한 번 교체 설치해야 하며 이후부터 앱 내 업데이트를 사용한다.

## 4. 제작자 릴리스: 개발 예정

수정 → 앱 버전 증가·변경사항 작성 → 테스트 → 빌드·코드서명 → 이전 설치본에서 업그레이드 검증 → GitHub Releases 초안에 파일 업로드 → 파일 검증 → 정식 공개 → 업데이트 안내 동작 확인.

소스 수정이나 로컬 빌드만으로 사용자에게 전달되지 않는다. 게시된 새 버전을 사용자가 확인·승인해야 적용된다. 파일 구성, 비밀키 관리와 출시 기준은 [DISTRIBUTION](DISTRIBUTION.md)을 따른다.
