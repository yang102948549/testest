# Windows EXE 배포·구매 인증·업데이트 설계

기준일: 2026-10-01 · 제품: **시험감독 배정 프로그램** · 제작자: **양양**

상태: **새 배포 정책의 설계 문서. 구현·배포 완료 문서가 아니다.**

## 1. 결정과 폐기 범위

공통 Windows x64 설치 EXE + 최초 실행 라이선스 파일 인증 + 사용자 승인형 앱 내 업데이트를 채택한다. 초기 배포 저장소는 GitHub Releases, 클라이언트는 `electron-updater`, 설치 형식은 기존 NSIS를 사용한다.

기존 ‘설치 중 CD키 입력’과 ‘패치마다 구매자에게 EXE를 개별 전달’하는 수동 배포 운영은 폐기한다. 이후 개발·출시는 이 문서를 기준으로 한다. 새 정책을 구현하기 전까지 기존 설치 파일을 새 정책 구현본으로 배포하지 않는다.

이번 작업은 문서 정리이다. 설치 스크립트·인증 코드·기존 EXE·발급 개인키를 삭제하거나 새 방식으로 변경하지 않았다. 기존 EXE는 구방식 검증 산출물로 취급한다. **현재 `npm run package` 역시 구방식 설치 파일을 생성한다.**

## 2. 목표 구조

| 요소 | 설계 |
|---|---|
| 설치 프로그램 | 모든 고객이 동일한 EXE 사용. 설치 단계에 구매 인증 입력 없음 |
| 구매 인증 | 구매자별 서명된 `.license` 파일을 최초 실행 시 선택 |
| 인증 보관 | 사용자 데이터 폴더. 앱 업데이트·설치 폴더 교체와 분리 |
| 업데이트 | `electron-updater`, 우선 stable 채널 하나 |
| 배포 저장소 | 소스와 분리한 공개 GitHub Releases. 설치 파일·메타데이터·변경사항만 게시 |
| 사용자 선택 | 비동기 버전 확인, 다운로드 승인, 저장 후 설치 승인 |
| 네트워크 단절 | 기존 인증·배정·저장 기능 계속 사용 |
| 코드서명 | 신뢰되는 인증서/서비스로 Windows EXE와 설치 프로그램 서명 |

공개 설치 파일의 다운로드를 구매자에게만 제한하지 않는다. 사용 권한은 앱의 라이선스 검증으로 통제한다. 비공개 저장소 접근 토큰을 고객 앱에 내장하지 않는다.

## 3. 라이선스 파일

- 현재 RSA-SHA256 기반을 재사용한다. 확장자뿐 아니라 제품·형식 버전·서명·필수 필드를 검증한다.
- 최소 내용은 형식 버전, 제품 ID, 라이선스 ID, 구매자 표시명, 발급 시각과 서명이다. 구매자 정보는 암호화된 정보로 취급하지 않는다.
- 기존 서명 토큰을 UTF-8 `.license` 파일 내용으로 사용하면 발급 자산을 유지할 수 있다. 파일 형식과 크기 제한은 구현 시 고정하고 테스트한다.
- 판매자는 구매 확인 후 파일을 발급해 전달한다. 결제·메일 자동 발송은 현재 범위에 넣지 않는다.
- 첫 실행에 ‘구매 인증 파일 선택’을 제공하고 인증 후 구매자 정보와 상태를 표시한다. 검증·저장은 메인 프로세스에서 처리한다.
- 재실행과 업데이트에 재인증을 요구하지 않는다. 잘못된 파일을 선택해도 기존 정상 인증을 보존한다.
- 영구·오프라인 인증이며 기기 수 제한·공유 감지·원격 폐기는 없다. 기존 라이선스는 패치에도 유효하다. 유료 메이저 업그레이드는 별도 정책 결정 전에는 구현하지 않는다.

### 발급 자산과 구버전 전환

현재 `.license-secrets/issuer-private.pem`은 발급 개인키, `build/license-public-key.json`은 검증 공개키이다. 개인키는 안전하게 별도 백업하고 저장소·EXE·릴리스 파일에 포함하지 않는다. 서명 키를 임의 재생성하지 않는다. 구매 인증 키와 Windows 코드서명 자격정보는 서로 다른 자산이다.

현재 `scripts/license-issuer.mjs`는 구방식 텍스트 토큰 발급 도구다. `.license` 발급 절차와 안내로 개편하고 판매자 사용법을 구현 후 확정한다. 기존 CD키를 발급한 경우 같은 공개키로 검증하여 새 로컬 인증 위치로 이전하는 호환 처리를 추가한다. 새 고객에게 CD키 입력 단계를 다시 도입하지 않는다.

## 4. 업데이트 동작

1. 앱 실행 후 업무를 막지 않고 업데이트를 확인한다. 직접 확인하는 메뉴도 제공한다.
2. 새 버전과 변경사항을 보여주고 다운로드 여부를 묻는다. 강제 다운로드·설치는 하지 않는다.
3. 다운로드 완료 후 무결성과 코드서명을 검증한다. HTTPS를 사용하며 검증 실패 시 설치하지 않는다.
4. ‘저장 후 업데이트’를 선택하면 계산 실행 여부, 임시 조정·저장 상태를 확인한다.
5. 반영·취소를 사용자가 결정하고 저장 성공과 백업을 확인한 다음 설치한다. 저장 실패 시 종료를 강행하지 않는다.
6. 새 버전을 실행해 기존 인증과 문서를 연다. 형식 변경이 있으면 검증된 마이그레이션을 수행한다.

일반 종료가 동의 없는 업데이트 설치로 이어지지 않도록 updater의 자동 다운로드·종료 시 자동 설치 기본값을 명시적으로 제어한다. 다운로드 실패와 설치 도중 실패를 구분한다. 설치 과정 오류에서 이전 실행 파일이 항상 자동 복원된다고 보장하지 않는다.

차등 다운로드는 해당 버전·배포 환경에서 지원 여부를 검증하여 활용할 수 있다. 초기 요구사항은 전체 설치 파일 다운로드로도 정확히 동작하는 것이다. 차등 패치나 자동 롤백을 이미 지원하는 것으로 안내하지 않는다.

## 5. 제작자 릴리스 운영

- GitHub 배포 저장소·URL은 아직 지정되지 않았다. 구현 시 소유 계정·저장소·stable 채널을 확정한다.
- 앱 버전은 패치마다 증가시키며 엔진·데이터 스키마 버전과 별도로 관리한다.
- 같은 빌드의 설치 EXE, `.blockmap`, `latest.yml` 등 해당 updater가 요구하는 파일을 함께 게시한다. 서로 다른 빌드의 해시·파일을 혼합하지 않는다.
- 초안 릴리스에서 파일·서명·업그레이드를 검증한 뒤 공개한다. 불완전한 업데이트 정보가 먼저 노출되지 않도록 한다.
- 업로드 토큰은 빌드 환경 또는 CI 비밀정보로 보관한다. 고객 앱에는 공개 읽기 주소만 포함한다.
- 자동 게시도 구현 후 별도 검증한다. 단순 빌드가 운영 릴리스 공개를 의미하지 않도록 한다.
- 장애 시 잘못된 릴리스 노출을 중단하고 수정된 더 높은 버전을 배포한다. 호환성 확인 없이 다운그레이드를 지시하지 않는다.
- 현재 업데이트 기능이 없는 1.2.0 사용자가 있다면 한 번의 교체 설치가 필요하다. 이후 패치를 EXE 개별 전달 방식으로 운영하지 않는다.

## 6. 데이터 보존·코드서명

설치 위치와 고사·라이선스 위치를 분리하고 기존 appId와 사용자 데이터 경로를 유지한다. 업데이트 전에 별도 버전 백업을 만들고 복구 경로를 문서화한다. 미래 스키마를 이전 버전이 잘못 덮어쓰지 않도록 호환성·마이그레이션을 테스트한다.

현재 `signExecutable: false` 설정은 새 배포 단계에서 교체한다. 인증서 제공 방식에 맞춰 서명·타임스탬프·게시자 검증을 구성한다. 인증서 갱신 시 updater의 게시자 검증과 호환성을 확인한다. 제품의 제작자 ‘양양’ 표기와 인증서의 검증된 게시자 이름은 구분한다. 서명만으로 SmartScreen 경고가 즉시 사라진다고 보장하지 않는다.

## 7. 비용·운영 책임

초기 GitHub 공개 Releases 기반은 별도 앱 서버·DB 없이 운영하는 것을 목표로 한다. 소스는 비공개로 유지할 수 있다. 코드서명 인증서/서비스, 유료 CI를 선택하는 경우의 비용은 별도다. 요금·서비스 제한은 가입 시 확인하며 영구 무료 보장으로 안내하지 않는다.

제작자의 반복 업무는 변경사항 작성, 테스트, 빌드·서명, 이전 버전 업그레이드 검증, 릴리스 공개와 장애 대응이다. 고객 데이터나 인증 확인을 위한 상시 서버 운영은 요구하지 않는다.

## 8. 구현 작업·출시 인수 기준

| 작업 | 완료 조건 |
|---|---|
| 설치 인증 제거 | 신규·무인·업데이트 설치 모두 CD키 입력 없이 설치 가능 |
| 최초 실행 파일 인증 | 정상·변조·다른 제품·손상·과대 파일, 취소, 재실행, 미인증 IPC 차단 검증 |
| 기존 인증 호환 | 정상 구토큰 이전, 잘못된 파일로 기존 인증 손상 없음 |
| 발급 도구 개편 | `.license` 생성, 개인키·공개키 일치 확인, 기존 발급 파일 덮어쓰기 방지 |
| updater 연결 | 새 버전·최신 버전·오프라인·취소·재시도·손상 다운로드 검증 |
| 종료·저장 연동 | 미반영 변경·계산 실행·저장 실패 시 설치 보류 |
| 데이터 유지 | 이전 실제 설치본에서 고사·인증·설정 유지, 마이그레이션 실패 복구 |
| 서명·릴리스 | 게시자 검증, 잘못된 서명 차단, 메타데이터 일치, 비밀정보 미포함 |
| Windows 검증 | 일반 사용자 권한 신규 설치·업데이트·재시작·제거 정책 확인 |

위 기준을 통과한 새 버전부터 공식 배포본으로 취급한다. 현재 CD키 테스트 통과 기록은 새 인증·업데이트의 인수 테스트를 대신하지 않는다.

참고: [업데이트 문서](https://www.electron.build/docs/features/auto-update/), [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation). 실제 도입할 라이브러리 버전의 API는 구현 시 다시 확인한다.
